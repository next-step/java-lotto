# 2단계 - 로또(자동)

## 나의 학습 목표

### 1. 네이밍 규칙을 지킨다.
- `-er`로 끝나는 이름을 사용하지 않는다.
- 클래스 이름은 클래스의 객체들이 무엇인지(what it is)에 기반해 이름을 짓는다.

### 2. TDD 사이클을 끝까지 지킨다.
- 테스트를 먼저 작성하고, 프로덕션 코드를 수정한다.
- Red -> Green -> Refactor 사이클을 일관되게 유지한다.
- 사이클 단위로 커밋한다.

### 3. 객체지향 생활 체조 원칙을 의식적으로 지킨다.
- 모든 원시값과 문자열을 포장한다.
- 일급 컬렉션을 사용한다.
- 한 메서드에 한 단계의 들여쓰기만 한다.
- else 예약어를 쓰지 않는다.

### 4. 주생성자와 부생성자를 명확히 구분한다.
- 주생성자는 필드 타입과 완전히 일치하는 생성자로 구현한다.
- 부생성자는 주생성자를 호출하는 방식으로 구현한다.
- 불필요한 기본 생성자는 만들지 않는다.

### 5. 책임 분리를 명확히 한다.
- Domain 객체는 View에 의존하지 않는다.
- 출력용 문자열 생성은 View가 담당한다.
- 핵심 비즈니스 로직은 Domain이 담당한다.

### 6. 점진적인 리팩터링 전략을 사용한다.
기존 코드에 영향을 최소한으로 미치면서 리팩터링한다.
1. **1단계**: AS-IS에 TO-BE 코드를 추가한다.
2. **2단계**: AS-IS에 의존하는 모든 코드를 TO-BE 코드를 사용하도록 점진적으로 리팩터링한다.
3. **3단계**: 의존하는 모든 코드가 TO-BE 코드를 사용하면 AS-IS 코드를 삭제한다.

### 7. 이전 단계의 피드백을 반영한다.
- 같은 피드백을 반복하지 않도록, 체크리스트를 점검한다.

## 이전 단계 피드백 체크리스트

### 원시값 포장
- [ ] 비즈니스 의미가 있는 원시값은 클래스로 포장했는가?
- [ ] 유효성 검증 로직이 해당 객체 내부에 캡슐화되어 있는가?
- [ ] 검증 메서드를 생성자에서 호출했는가?

### 생성자 패턴
- [ ] 주생성자(필드 타입 일치)가 존재하는가?
- [ ] 부생성자가 주생성자를 호출하는가?
- [ ] 불필요한 기본 생성자가 없는가?

### 책임 분리
- [ ] Domain 객체가 View에 의존하지 않는가?
- [ ] 객체의 값을 꺼내지 않고 메시지를 보내는가?
- [ ] static 인스턴스 변수를 사용하지 않았는가?

### 테스트 코드
- [ ] 경계값 위주로 테스트했는가?
- [ ] 객체 단위로 비교했는가?
- [ ] 테스트용 생성자를 활용했는가?
- [ ] @DisplayName에 구체적 데이터를 포함하지 않았는가?
